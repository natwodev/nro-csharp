2. ### 0.3 Notation in the "Field structure" column

`b` = byte (1 byte) · `s` = short (2 byte big-endian) · `i` = int (4) · `L` = long (8) · `C` = "cris" = 4-byte int if `Manager.readInt == true` (default), otherwise 8-byte long (§2.3) · `u` = UTF string (§2.2) · `z` = bool (1 byte) · `raw` = raw byte string · `n×{…}` = repeated n times · `[…]` = conditional/optional · "sub" = the first payload byte selecting the branch (cmd that has a sub-command).

In the cmd table (§3): `receive:` = where that packet is read/handled; `build:` = where that packet is created/written (server side: `new Message(...)`; client side: `Service.cs`). "C→S" = client sends, server receives; "S→C" the opposite.

### 0.4 Summary of what must be remembered when porting

1. All multi-byte numbers are **big-endian**; `cmd` is a **signed byte**; `size` is **u16 big-endian** (or 3 bytes little-endian with `−128` for 8 S→C cmds, §1.4).
2. Encryption = rolling XOR with the 24-byte key `NguyenDucVuEntertainment`; **two independent pointers** (read/write), the same pointer for cmd + size + payload; the `-27` packet is not encrypted (§1.2-1.3).
3. The client opens with an empty `-27`; the server replies `-27` (25-byte payload) and **only then** turns encryption on and **only then** starts sending other packets (§1.3).
4. The real login flow: `-27` → `-29/2` → `-29/0` → `-28/4` → (`-87`, `-28/6|7|8`) → `-28/13` → burst of character packets + `-24` → `-39` (§4).
5. HP/MP/damage are `cris` (4-byte int when `readInt=true`); power/potential are real longs; gold is a long only when `version >= 214` (§2.3, §5.C).
6. The item option on the wire is `(int, int)` on the server but `(ubyte, ushort)` on the client in the repo — **not matching** (§5 D2).
7. The server's list of 3-byte sizes has `-28`, the client in the repo does not — **a decision must be made and tested with a real client** (§5 A1).
8. The server silently drops every unknown cmd and swallows most exceptions; the incoming queue is cut at 500 packets (§1.6).
9. The constant names in `Cmd_message.java` are not trustworthy; only the literal values and the code behavior are the truth (§3.1).
10. A connection that has not logged in successfully is disconnected by the server after 100 ticks (~100 s) from the moment TCP connects (§4.1); on a duplicate login the old session is kicked immediately inside `GodGK.login` (§4.3a), with no 1 s wait on the normal path.
11. There are 7 top-level cmds that are live but have no constant in `Cmd_message.java`: `11, 2, 0, 1, 3, -109, 103` (§3.2b).

## 1. Packet framing

### 1.1 Byte-by-byte format

Both directions use the same frame. After the key has been established (§1.3), each packet consists of:

```
offset  length   content
0       1        cmd  (SIGNED byte: Java `byte`, C# `sbyte`), encrypted by XOR with 1 key byte
1       2        size (u16 big-endian: high byte first), each byte encrypted by XOR with 1 key byte     [normal cmd]
1       3        size 3 bytes, low→high, (key XOR byte) − 128                                [S→C only, cmd in §1.4]
3 (or 4)  size  payload; each byte encrypted by XOR with 1 key byte
```

- `cmd`: 1 signed byte. Java: `byte`; written with `dos.writeByte` (`network/io/MessageSendCollect.java:60-65`); read with `dis.readByte()` (`:21`). Client: `sbyte` (`Session_ME.cs:177`).
- `size` = the number of payload bytes, **not** including cmd and the size field itself. Valid range for the 2-byte form: 0..65535. There is no overflow check: the server writes `(byte)(size >> 8)` and `(byte)(size & 0xFF)` (`MessageSendCollect.java:80-83`) so a payload > 65535 bytes on a cmd not in §1.4 will have its size truncated → stream desync (§5).
- The minimum frame length = 3 bytes (cmd + 2 size bytes, empty payload).
- Before the key exists (only the `-27` packet): cmd 1 raw byte, size 2 raw big-endian bytes, raw payload (`MessageSendCollect.java:64`, `:85`, `:92`).

### 1.2 Rolling XOR encryption

- **Default key**: the ASCII string `NguyenDucVuEntertainment` = 24 bytes, hex `4e677579656e4475635675456e7465727461696e6d656e74` (`network/session/Session.java:59`, `this.KEYS = "NguyenDucVuEntertainment".getBytes()`). Every session uses the same key; there is no per-session key. `MySession.KEYS = {0}` (`network/session/MySession.java:37`) and `sendSessionKey()` (`:115-128`) are dead code — nobody calls them (checked by grep).
- **Pointers separate per direction**: the receive side uses `curR`, the send side uses `curW`, both initialized to 0, each belonging to one `MessageSendCollect` instance (one instance/session, `nro/server/ServerManager.java:532`). Client: `curR`/`curW` are `static sbyte` (`Session_ME.cs:255-257`), reset to 0 in `cleanNetwork` (`:486-490`).
- **Operation**: `out = K[p] XOR in` (all 8 bits), then `p = p + 1`, and if `p >= len(K)` then `p %= len(K)` (`MessageSendCollect.java:47-54` `readKey`, `:102-109` `writeKey`; client `Session_ME.cs:429-447`). Encryption and decryption are the same XOR operation.
- **Applied to which bytes, in exact key-consumption order** (a single pointer per direction): (1) the cmd byte; (2) the size bytes (2 or 3 bytes); (3) each payload byte from start to end. No byte of the frame is skipped once the key is on (`MessageSendCollect.java:21-43` read; `:59-92` write).
- The key packet `-27` is NOT encrypted and does NOT advance the pointer; the first encrypted byte of each direction uses `K[0]`.
- The decision "encrypted or not yet" is based on a flag: server `session.sentKey()` (read: `MessageSendCollect.java:22,26,39`; write: `:60,79,87`), client `getKeyComplete` (`Session_ME.cs:178,187,204,372,384,395`). The server turns the flag on right after finishing writing the key packet (`network/io/KeyHandler.java:19-21`); the client turns it on when it receives the key packet (`Session_ME.cs:135`).

### 1.3 The first packet `-27` and how the server sends the key

1. Right after TCP connects, the client sends an empty unencrypted `-27` packet: 3 bytes `E5 00 00` (`Session_ME.cs:343-358`; line 356 `doSendMessage(new Message(-27))`, going through the no-key branch: cmd at `:379`, size `(ushort)0` at `:416` because `getData()` returns null). The client keeps `getKeyComplete = false` from `connect()` (`:314`) and the send queue is only flushed once there is a key (`Sender.run`, `:33`).
2. The server's read thread (`network/Collector.java:32-48`) intercepts every packet with `command == -27` on the server-side socket and calls `session.sendKey()` (`:37-41`) — this packet is **not** put into `QueueHandler`; the `case -27` branch in `nro/server/Controller.java:663-665` is dead code.
3. `MySession.sendKey()` (`network/session/MySession.java:110-113`) → `KeyHandler.sendKey` (`network/io/KeyHandler.java:10-24`): builds `Message(-27)` with a payload consisting of: `byte len` (= 24), `byte K[0]`, then for i = 1..23 `byte (K[i] XOR K[i-1])` → **25 payload bytes**. This packet is written by `session.doSendMessage` (synchronous write, bypassing the queue) while `sentKey == false` so it goes out raw; afterwards `session.setSentKey(true)` (`KeyHandler.java:19-21`).
4. `MyKeyHandler.sendKey` (`network/io/MyKeyHandler.java:13-17`) additionally calls `DataGame.sendDataImageVersion` (an empty function: the body is commented out, `Data/DataGame.java:204-220`) and `DataGame.sendVersionRes` (packet `-74` sub 0 + `int vsRes=4`, `DataGame.java:410-421`, queued). Then `MySession.sendKey` calls `startSend()` (`MySession.java:112`) to start the send thread: **before receiving `-27` from the client, the server flushes no packet at all**, because `sessionInit` only runs `startCollect().startQueueHandler()` (`nro/server/ServerManager.java:531-535`).
5. The client decodes the key (`Session_ME.cs:121-147`): reads `sbyte len`, `len` bytes, then `for j in 0..len-2: key[j+1] ^= key[j]` (recovers the original key by the XOR chain), sets `getKeyComplete = true` (`:135`). After that the client tries to read more `u IP2`, `i PORT2`, `b isConnect2` (`:136-138`) — **the Java server does not send these fields**; `readUTF` throws an exception and `catch (Exception) {}` (`:144-146`) swallows the error. Consequence: `GameMidlet.IP2/PORT2/isConnect2` are never assigned from this packet.
6. Test vector for the key packet on the server side: see §1.7.

### 1.4 Cmds that use a 3-byte size

Both sides only use a 3-byte size in the **S→C** direction; the client always sends a 2-byte size (`Session_ME.cs:384-390`), the server always reads a 2-byte size (`MessageSendCollect.java:25-32`).

| | Java server (write) | Unity client (read) |
|---|---|---|
| Cmd list | `-32, -66, -74, 11, -67, -87, 66, -28` (`MessageSendCollect.java:71-72`) | `-32, -66, 11, -67, -74, -87, 66, 12` (`Session_ME.cs:182`) |
| Condition | `msg.command` is in the list, **independent of `sentKey`** (the branch at `:71-78` runs before `sentKey` is considered) | after decoding cmd (`:178-181`); the read branch is `readMessage2` (`:149-171`) |
| Size byte formula | with `s` being in turn `size & 0xFF`, `(size>>8) & 0xFF`, `(size>>16) & 0xFF`: `wire = ((K[p++] XOR s) − 128) & 0xFF` (`:73-78`, `dos.writeByte(b2 - 128)` with `b2` being a `byte`) | `v = readKey(wire) + 128` with `readKey` returning `sbyte`; (`:151-153`) |
| Order | low byte first → high byte after (little-endian) | `size = ((v2 * 256) + v1) * 256 + v0` with v0 read first (`:153`) |
| Equivalent | `wire = (K XOR s) XOR 0x80` | `s = K XOR (wire XOR 0x80)` |

- Both formulas match mathematically: checked by simulation (send–receive loop with size 0, 1, 255, 256, 300, 65535, 65536, 70000, 200000 all recover correctly). Theoretical limit 2^24−1 = 16 777 215 bytes.
- **The two sides do NOT match on the list**: the server has `-28`, the client does not; the client has `12`, the server never sends cmd 12 (there is no `new Message(12)` anywhere in `src/`). The server's own note at `MessageSendCollect.java:68-70` admits that "both the server and Unity Session_ME must treat `-28` as extended", but `Game1/Session_ME.cs:182` does not have it yet. With this client, every `-28` packet from the server (including `-28/4` right after login) will have its size read wrongly → see §5 item A1.
- `Session_ME2.cs:179` (the secondary connection) is also missing both `66` and `12`.

### 1.4b Reference pseudocode (extracted from the code, not the original code)

```csharp
// Each direction has its own pointer p (0-based) over the key K (byte[24]); p is initialised to 0 for every session.
byte Next(byte b) { byte r = (byte)(K[p] ^ b); p++; if (p >= K.Length) p %= K.Length; return r; }

// WRITE (server -> client) when sentKey == true   [MessageSendCollect.doSendMessage]
void WritePacket(sbyte cmd, byte[] data) {
    Out.WriteByte(Next((byte)cmd));
    int size = data.Length;
    if (cmd is -32 or -66 or -74 or 11 or -67 or -87 or 66 or -28) {      // §1.4
        Out.WriteByte((byte)(Next((byte)(size & 0xFF)) - 128));           // low byte first
        Out.WriteByte((byte)(Next((byte)((size >> 8) & 0xFF)) - 128));
        Out.WriteByte((byte)(Next((byte)((size >> 16) & 0xFF)) - 128));
    } else {
        Out.WriteByte(Next((byte)(size >> 8)));                            // high byte first (big-endian)
        Out.WriteByte(Next((byte)(size & 0xFF)));
    }
    foreach (var b in data) Out.WriteByte(Next(b));
}

// READ (server <- client) when sentKey == true   [MessageSendCollect.readMessage]
sbyte cmd = (sbyte)Next(ReadByte());
int hi = Next(ReadByte()); int lo = Next(ReadByte());                      // always 2 bytes on the C->S side
int size = (hi << 8) | lo;
var data = ReadExactly(size); for (int i = 0; i < size; i++) data[i] = Next(data[i]);
```

### 1.5 Packets without a payload

- **Server write**: a newly created `Message` has an empty `ByteArrayOutputStream` → `getData()` returns an empty array (not `null`, `network/io/Message.java:48-50`). Normal write path: `cmd` (encrypted) + size 0 (2 encrypted bytes, or 3 bytes if the cmd belongs to §1.4) + no payload. The `data == null` branch → raw `dos.writeShort(0)` (`MessageSendCollect.java:93-95`) almost never runs (it only happens with a `Message` built in read mode, in which case `os == null` causes an NPE right in `getData()`).
- **Client write**: `myWriter.getData()` returns **`null`** when nothing has been written (`myWriter.cs:129-133`); `doSendMessage` then writes size 0 with `writeKey(0)` twice (`Session_ME.cs:405-411`) — i.e. the two size bytes are `K[p]`, `K[p+1]` themselves; before the key exists it writes `(ushort)0` (`:416`). The result is still exactly 3 bytes `cmd + size`.
- Receive: size 0 → no payload is read (server `MessageSendCollect.java:33-38`: `new byte[0]`).

| Item | Behavior | Evidence |

## 2. Primitive data types in the payload

### 2.1 Mapping table

The server uses `java.io.DataOutputStream`/`DataInputStream` through `network/io/Message.java` (`writer()`/`reader()`, the wrapper methods `:119-247`). The client uses `myWriter`/`myReader` (not `System.IO`); every multi-byte number is **big-endian**.

| Type | Java server | Wire | C# client |
|---|---|---|---|
| byte | `writeByte(int)` writes the low 8 bits; `readByte()` is signed | 1 byte | `myWriter.writeByte(sbyte)` and `writeByte(int)` (`myWriter.cs:34-42`); `myReader.readByte()`→`sbyte`, `readUnsignedByte()` (`myReader.cs:29-47`) |
| bool | `writeBoolean` → 1 byte `01`/`00`; `readBoolean` is true when ≠ 0 | 1 byte | `writeBoolean` writes 1/0 (`myWriter.cs:87-90`); `readBool/readBoolean` is true when `> 0` (`myReader.cs:105-113`), i.e. a byte ≥ 0x80 is treated as false |
| short | `writeShort(int)` low 16 bits, BE | 2 bytes | `writeShort` (`myWriter.cs:59-76`); `readShort` (`myReader.cs:49-61`) |
| int | `writeInt` BE | 4 bytes | `writeInt` (`myWriter.cs:78-85`); `readInt` (`myReader.cs:77-89`) |
| long | `writeLong` BE | 8 bytes | `myReader.readLong` 8 bytes BE (`:91-103`); **the client has no `writeLong`** (it never writes a long to the server) |

### 2.2 UTF strings — notes for porting

- The length is a u16 (at most 65535 **bytes** after encoding). Java `writeUTF` throws `UTFDataFormatException` if longer; in that case the builder catches the exception, logs it and does not send the packet.
- Java uses *modified UTF-8*: the character U+0000 is encoded as `C0 80`; characters outside the BMP are encoded as two 3-byte surrogates (CESU-8). The client uses standard UTF-8 (`UTF8Encoding`), so these cases decode differently. Vietnamese text (BMP) does not differ.
- **The C→S direction is more serious than the S→C direction.** The server reads strings with `java.io.DataInputStream.readUTF` (via `msg.reader()`, `network/io/Message.java`), the JDK's modified-UTF-8 decoder. The client writes standard UTF-8 (`myWriter.cs:92-106`). Consequences confirmed by running a real JDK (vectors `readCases` of `tests/golden/utf.json`):
  - Standard 4-byte UTF-8 (`F0 9F 98 80`, any character outside the BMP such as emoji) is **REJECTED**: `UTFDataFormatException` (vector `standard-utf8-4byte-rejected`). Also rejected: a lead byte `80..BF` or `F0..FF`, a following byte that is not `10xxxxxx`, a string truncated in the middle of a character. In the server, the exception propagates up to `Controller.onMessage` (only logged, the connection is kept, §1.6) ⇒ the whole packet (chat, rename, string input…) is silently dropped.
  - ACCEPTED although not standard UTF-8: a bare byte `00` (becomes U+0000, vector `raw-nul-00`), overlong forms (`C1 81` and `E0 81 81` both become `A`; vectors `overlong-2byte-A`, `overlong-3byte-A`), `C0 80` (U+0000), each surrogate encoded separately in 3 bytes (`ED A0 BD ED B8 80` becomes a surrogate pair = U+1F600).
  - A declared length larger than the remaining data ⇒ `EOFException`; extra trailing bytes after the length is satisfied are not read (`trailing-bytes-left-unread`).
  - A port that uses the standard .NET UTF-8 decoder will accept emoji and replace bad bytes with U+FFFD instead of dropping the packet ⇒ behavior differs from Java. The port must write its own modified-UTF-8 decoder for the C→S read path, throw errors for exactly the cases above, and let that error lead to "drop the packet, keep the connection".
- The client reads the length with a signed `readShort()` → a string of length ≥ 32768 bytes makes `new byte[num]` negative and throws an exception (`myReader.cs:117-118`).
- Strings used as two-way parameters (character name, chat, URL…) always follow this format.

### 2.3 Special cases in `Message`

- **`writeCris(long v, boolean is)`** (`network/io/Message.java:52-58`): `is == true` → `writeInt((int) v)` (4 bytes, truncated to the low 32 bits), otherwise `writeLong(v)`. Every call site passes the static flag `Manager.readInt` (`nro/server/Manager.java:95`, default `true`) together with `Util.CrisGH(double)` (`Utils/Util.java:465-473`) to clamp the value to `Integer.MAX_VALUE` when the flag is on. Used for HP/MP/damage/…; grep finds ~110 matching lines in `src/` (including commented-out lines).
- **Corresponding client**: `Message.readLong()` (`Message.cs:55-62`) reads a **4-byte int** when `ModFunc.isReadInt` (default `true`, `ModFunc.cs:41`), otherwise an 8-byte long. The two flags (`Manager.readInt` on the server side, `ModFunc.isReadInt` on the client side) **must be equal**; currently they are independent of each other, and no packet transmits this flag.
- **The client mixes two ways of reading a long**: `msg.readLong()` (flag-dependent) appears 65 times in `Controller.cs`; `msg.reader().readLong()` (always 8 bytes) appears 15 times. Therefore a long field must be ported as the correct kind: HP/MP/damage use `cris`; power, potential, gold (`version>=214`) use a real long (see each packet in §3).
- **`writeShortToLong(long, boolean)` and `writeByteToLong(long, boolean)`** (`Message.java:60-74`): the same flag mechanism (short/byte or long) but **no call site** in `src/` (checked by grep).
- **`readInt3Byte()`** (`Game1/Message.cs:44-47`) actually calls `dis.readInt()` — reads **4 bytes**, the name is misleading; no call site.
- **`Message.writeImage/readImage`** (`Message.java:254-270`): `int length` + image bytes; no call site.
- **`Message(int command)`** casts to `(byte)` (`Message.java:21-23`): a literal outside [-128, 127] is truncated modulo 256. Example: `new Message(-218)` at `nro/services/Service.java:316` is actually cmd `38` (`OPEN_UI_SAY`).
- **cmd constants**: `network/logic/Cmd_message.java` is not referenced from any other Java file (checked by grep) — all code uses numeric literals. The constants there are only a reference catalog, and many names have drifted in meaning from how they are used (§3.1).

**Login deadline (a connection that has not logged in is disconnected after 100 ticks).** Each `MySession` carries `byte timeWait = 100` (`network/session/MySession.java:32`). The "Update Client" thread (`nro/server/Client.java:43-45`, the `run` loop sleeps `max(1000 − processing time, 10)` ms, `:449-460`) iterates over every session in `SessionManager` on each tick: if `timeWait > 0` it decrements by 1, and when it reaches 0 it calls `kickSession` (`:426-446`, condition at `:438-442`). There is only ONE place that sets `timeWait = 0`: on successful login, after `Client.safePut` and `sendSmallVersion`/`sendBgItemVersion` (`MySession.java:207`). Consequences for the port: (a) from the moment TCP connects (the session is `putSession`-ed at `network/Network.java:133`), the client has approximately **100 seconds** to complete login, regardless of whether it has exchanged keys, is downloading resources (phase B), is synchronizing data (D) or is on the character creation screen; on expiry the server disconnects, without sending any packet; (b) the counter is not reset on a failed login or on receiving any packet, so every wrong-password attempt also eats into the same 100 ticks; (c) once `timeWait` is already 0 the session is never kicked by this mechanism (if it disconnects for another reason after logging in, it goes through the normal `Collector`/`kickSession` path). The unit is the loop "tick" (~1 s per tick, longer if one `update` runs long), not an exact clock — ≈100 s is a nominal value inferred from the code, not measured.

### 5.F Other things to know

- **Unused cmd constants**: `Cmd_message.java` is not referenced; the 75 constants in §3.2 have no server-side code path (34 constants labeled `unknown` + 41 constants `only the client has a handler`) and 1 constant `only the server has a case` (`SKILL_UP` = `-30/17`). Do not try to "implement" the `unknown` constants (there is no code path). Note the converse: an `unknown` constant name does NOT mean that numeric value is dead at top level — e.g. `REQUEST_NPCTEMPLATE`=11 is a dead sub of `-28`, while the top-level cmd `11` (mob template) is live; the 7 live top-level cmds without a constant (`11, 2, 0, 1, 3, -109, 103`) are described in full in §3.2b and MUST be ported according to that row.

- **Time dependence**: the 33 ms tick of Sender/QueueHandler (latency), `SECOND_WAIT_LOGIN`=10 s (blocks re-login), the 1 s delay thread in `Controller.sendInfo` (title, disciple follow) — the order of these delayed packets relative to other packets is not fixed. **Login deadline: a connection that has not logged in successfully is disconnected by the server after 100 ticks (≈100 s)**: `MySession.timeWait = 100` (`network/session/MySession.java:32`), the "Update Client" thread decrements it every ~1 s tick and calls `kickSession` when it reaches 0 (`nro/server/Client.java:426-446,449-460`); it is set back to 0 only on successful login (`MySession.java:207`). Details and consequences in §4.1. The port must keep this behavior (even when the client is on the character creation screen or downloading resources).
- **Hidden state**: many packets are sent only when a state flag is on (`player.isNewMember`, `TASK_0_0`, `EventManager.*` events choosing the `eff_map*` file at `Zone.java:931-940`, `Manager.LOCAL`, `Maintenance.isRunning`).
- **Misnamed constants** (see §3.1): do not name the C# enum after `Cmd_message`; name it after the real meaning in the code, keeping the numeric value.

### 6.1 Script that checks all cmd constants are present

`port-csharp/tools/check_protocol_doc.py` (Python 3 only, runnable with `python -I`) reads `network/logic/Cmd_message.java`, strips comments and COMPUTES the value of each `static final` constant declaration (decimal, hex, octal, binary, negative numbers, casts such as `(byte) 0xFF` = -1, declarations split across lines, several variables in one statement; an expression that cannot be computed is an error, code 2), then compares only against the table located under section `3.2` (from the `3.2` heading to the next heading; code blocks and HTML comments are skipped). Each constant must have EXACTLY ONE row with the same name and the same value; duplicate rows, extra rows and malformed rows are reported; a row moved to another table counts as missing. Each row must have all 6 cells, the Direction cell must start with `C→S`/`S→C`/`both`/`unknown`, the Direction and Field structure cells must not be empty/`TODO`/dash (Field structure minimum 8 characters), the server/client cells must not be empty/`TODO` (use `—` if there is none). The output is in English. Exits with code 1 if there are problems, code 0 if complete, code 2 on a file read/parse error. The script does NOT check the correctness of the cell contents (actual direction, file:line, structure) — that is checked only by manual reading/separate cross-checking; the §3.2b table (7 cmds without a constant) is outside the scope of the script.

Self-test suite of the script: `python -I port-csharp/tools/tests_protocol/test_check_protocol_doc.py` (creates a temporary copy and breaks it in each way — deleting a constant, changing a value, renaming, an empty document, moving a row to another table, every column set to TODO, Java constants in hex/cast/split-line form, a wrong value hidden behind an extra row — and confirms the script catches it).

```
python -I port-csharp/tools/check_protocol_doc.py --java-src <path-to-Java-src> --doc nro-csharp/docs/PROTOCOL.md
```

The two parameters have defaults computed from the script's location (`<root>/source-game/SRC_6/AWN_Version/AWN_Version/src` and `<root>/nro-csharp/docs/PROTOCOL.md`, where `<root>` is the parent directory of `port-csharp/`).

### 6.3 Uncertainties / items needing further verification

1. **Which client is actually used with this server?** The client in `client-mod/Project_Client_Mod_Online/…/Game1/` deviates from the server at HIGH points (A1, D2, D3). If the target client is a different build (the files in `client-mod/Mod_APK_Online`, `Mod_IPA_Online`, `Mod_PC_Online` have not been analyzed). The most important candidate has also NOT been analyzed: the client that ships with this very server, `source-game/SRC_6/AWN_Version/Mod_Local/Panel Game.exe` (a Unity IL2CPP build with `GameAssembly.dll`, `Panel Game_Data/`). Per decision D11 of the plan (provisionally fixed), this is the target client (acceptance standard); the only evidence seen so far is strings (`global-metadata.dat` has `readMessage2`, `isReadInt`, `getKeyComplete`, `IP2`, `PORT2`) showing the same code family as the Unity source in the repo, but cross-checking the mismatches A1, D2, D3 against this build has NOT been done — so it is not known whether the target client treats `-28` as a 3-byte-size cmd, and the whole "client" column of the table is for reference only; the source of truth remains Java.
2. **List of 3-byte sizes** (A1): it is not known whether the target client has `-28` ⇒ must be tried with a real client before finalizing.
3. **Context assigned to constants with duplicate values** (§3.1) is based on the declaration block + observed usage; the "unknown" constants have no references so the context cannot be asserted.
4. **Packets with many variants** (`-81`, `-96`, `-45`, `-124`, `-128`, `-95`, `101`, `102`, `-86`, `-44`, `-103`, `-60`, `-12`, `-9`, `-20`, `127`): not all sub variants have been listed; each builder location must be read when porting the corresponding feature.
5. **Indirectly built packets**: the "server sends" set is computed from `new Message(<literal>)` and the functions `messageNotMap/NotLogin/SubCommand/ReadOpt`. If there is code that builds a `Message` with a variable (checked by grep: only `Service.sendMessage(MySession,int,String)` at `Service.java:2024-2034`, with no callers) it is outside the table.
6. **`Controller2.cs` and `Controller.cs` both run for each packet**: if a cmd appears in both files the client handles it twice; at the outermost `case` level there is currently no cmd duplicated between the two files (checked by script), but the sub-case level inside has not been checked.
7. **The fields `deltaTime`, `isNewMember`, `aura/effFront/hat`** in `-30/0` and similar: the client wraps the tail part in `try/catch` (`Controller.cs:5557-5567`) so a few missing/extra trailing bytes do not break the flow; this should not be taken as permission to drop the fields when porting.
8. **Tick** (33 ms) and the 1 s delay thread in `sendInfo` are behavior of the current server; the client may implicitly depend on the arrival order of the delayed packets.
